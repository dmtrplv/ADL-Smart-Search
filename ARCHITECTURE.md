Объяснение «сверху вниз» простым языком: что за компоненты, как устроен поиск
и ранжирование, какие есть ручки и где механизм упирается.

Актуально для текущей версии (коммит `3c3a789`, октябрь 2026).

## 1. Общая картина: три этажа

Приложение Streamlit-овое: браузер показывает страницу, а весь Python-код
выполняется на твоей машине (или рядом с exe).

```
        ┌─────────────────────────────────────────────────────┐
        │  1. ПОДГОТОВКА (редко, офлайн): индексация .adl      │
        │     adl_parser → index_store → data/local, data/ckm │
        └───────────────────────┬─────────────────────────────┘
                                │  JSON с текстами + .npy с векторами
        ┌───────────────────────▼─────────────────────────────┐
        │  2. ПОИСК (каждый запрос):                           │
        │     понять запрос → сравнить со всеми → отобрать 3–10│
        └───────────────────────┬─────────────────────────────┘
                                │  выбранные документы
        ┌───────────────────────▼─────────────────────────────┐
        │  3. ОТВЕТ ИИ (RAG): собрать контекст → спросить LLM  │
        └─────────────────────────────────────────────────────┘
```

Ключевая идея: **поиск не читает .adl-файлы каждый раз**. Один раз строится
«библиотечный каталог» — индекс: тексты + числовые «отпечатки смысла» (векторы).
Поиск работает только по каталогу, поэтому быстрый.

## 2. Что происходит при запуске

1. Определяется режим путей: запуск из проекта (`dev`) → `<project>/data` и
   `<project>/config` + `<project>/.adl-local`; собранный exe (`exe`) → сохранённый
   `bootstrap.json` или штатная папка `C:\emiastemplates\Soft\ADL Smart Search`
   + `%LOCALAPPDATA%\ADL-Smart-Search`. Если штатной папки нет, показывается экран
   выбора корня репозитория `emiastemplates` через «Обзор»; автопоиска по диску нет.
   Явные `ADL_REPO_ROOT` (корень Git-репозитория) / `ADL_DATA_ROOT` (папка с
   `config/` и `data/`) / `ADL_INDEX_DIR` / `ADL_LOCAL_DIR` имеют приоритет.
2. Читаются настройки: `.env` из локального config, `<data_root>/config/.env`, затем
   базовые `<data_root>/config/settings.json`, `llm.json` и `prompts.json`,
   поверх — пользовательские overrides из `%LOCALAPPDATA%\ADL-Smart-Search\config`.
   Системные переменные окружения важнее `.env`. В `.env` из LLM-настроек
   хранятся только секреты. Текстов промптов в коде нет: если `prompts.json`
   отсутствует или в нём пустой обязательный ключ, поиск продолжает работать,
   а ошибка показывается только при обращении к LLM.
3. Рисуется переключатель **dev-режим** только там, где он доступен: при запуске
   из Python (`--dev` / `ADL_DEV_MODE=1` включают его сразу) или в админской
   exe-сборке с маркером `dev_mode.enabled` рядом с exe. В стандартной exe-сборке
   переключателя и dev-панели нет. Если режим включён — над разделами появляется блок
   «Настройки (dev)»; его значения складываются в `SidebarState` и перекладываются
   в `cfg`. При запуске из проекта dev-режим пишет изменения в базовый
   `<project>/config/settings.json`, `llm.json` и `prompts.json` и убирает
   совпадающие ключи из overrides (админский режим правки конфига).
   В пользовательском режиме виджетов нет — `SidebarState` собирается из `cfg`/эффективных
   настроек.
   Провайдер ответов выбирается радиокнопкой в сайдбаре чата
   («ГигаЧат» ↔ «МЭШ.ИИ.Хаб») только на время сессии. Выбор не сохраняется:
   при каждом запуске по умолчанию активен МЭШ.ИИ.Хаб. В `config/llm.json`
   хранятся настройки обоих провайдеров, а не выбор активного.
   В dev-режиме можно выбрать отдельную модель для перевода и расширения запроса
   (по умолчанию — та же, что для ответов). Внутри МЭШ.ИИ.Хаб можно смешивать
   `aiedu-v2` и `mosgpt`: провайдер вспомогательной модели берётся из каталога.
   Для запросов создаются два независимых экземпляра провайдера, чтобы статистика
   и история ответов не смешивались.
3. `discover_sources` решает, какие источники живы: локальная база всегда,
   CKM — если указана папка или уже есть её индекс. CKM индексируется только
   по английским `term_definitions`: архетипы без английской версии и переводы
   на другие языки (включая русский) в индекс не попадают.
4. `load_all` читает `local/` и `ckm/` и **склеивает** документы и векторы в единые
   массивы. Каждому документу принудительно ставится метка `source` — иначе потом
   не отличить, откуда он.
5. Векторы нормируются (длина = 1) — после этого «близость» = просто скалярное произведение.
6. Строятся словари токенов (`token_vocab`) — чтобы короткие аббревиатуры вроде «ИВЛ»,
   «ЧСС» могли участвовать в поиске, а случайные двухбуквенные обрывки — нет.
7. Модель эмбеддингов **не грузится на старте**: запускается фоновый прогрев,
   чтобы первый поиск не «висел» 10 секунд.
8. Рисуется переключатель разделов «Архетипы»/«Поля»; рендерится только выбранный.
   Левый сайдбар отдан чату с ИИ.

Важная деталь: индексы кэшируются в памяти сессии (`st.session_state`),
а совместимость индекса с моделью проверяется по мете в JSON — сравнением имени
модели, без загрузки самой модели.

## 3. Индексация: как .adl превращается в «каталог»

### 3.1. Разбор файла (`adl_parser.py`)

Из каждого `.adl` достаётся три вещи:

- **`full_context`** — компактный читаемый текст: блок `МЕТАДАННЫЕ` (цель,
  использование, ключевые слова, недопустимое использование) + `СТРУКТУРА`
  (до 350 узлов: имя, at-код, типы `DV_*`, единицы, значения, описания).
  Это то, что потом увидит ИИ.
- **`anchor`** — «концентрат для поиска»: главное имя трижды + до 30 названий/описаний
  полей + цель/использование/ключевые слова. Именно anchor превращается в вектор.
  Блок «недопустимое использование» в anchor **не входит** — он хранится отдельно,
  чтобы не притягивать документ по словам из запретов.
- **Поля** (`extract_field_chunks_from_compact`) — для второго раздела: каждое листовое
  поле становится отдельным «документом» с именем, at-кодом, путём
  (`родитель > ребёнок`), типом, единицами и значениями.

### 3.2. Два вида документов

| | Архетип (раздел 1) | Поле (раздел 2) |
|---|---|---|
| Единица поиска | один `.adl` целиком | каждый лист структуры |
| Что в векторе | anchor | `поле поле at-код \| текст` |
| Зачем | «найди подходящий архетип» | «найди конкретное поле/параметр» |
| Сколько было у нас | ~1.1k local + ~0.7k ckm | ~15.6k local + ~6.8k ckm |

Поэтому поиск по полям — самая «тяжёлая» операция: сравнение идёт с десятками тысяч записей.

### 3.3. Векторы

Модель `paraphrase-multilingual-MiniLM-L12-v2` превращает текст в 384 числа —
«координаты смысла». Близкие по смыслу тексты получают близкие координаты,
даже если слова разные и даже на разных языках (модель мультиязычная).

Хранится это так:

```
data/
  settings.json            # папки + строгость
  local/  archetype_data.json, archetype_vectors.npy
          field_data.json,     field_vectors.npy
  ckm/    ... то же самое
```

`*_data.json` — тексты и метаданные (включая `embed_model`/`embed_dim`),
`*_vectors.npy` — матрица чисел. Если индекс собран другой моделью, приложение
честно скажет «пересоберите».

### 3.4. Инкрементальность

Повторная индексация не пересчитывает всё: файл считается неизменным по
`mtime`+`size`, затем по `sha1`; у полей — по `sha1` всего `.adl`.
Неизменённые векторы переиспользуются. Полная пересборка — отдельная кнопка.

## 4. Поиск и ранжирование — подробно

Это сердце приложения. Весь путь одного запроса — семь шагов.

### Шаг 0. Запрос превращается в 1–2 «рабочие» версии

- **Расширение (по желанию)**: кнопка «Предложить расширения» просит ИИ дать
  синонимы; выбранные галочками варианты склеиваются с запросом:
  `настройки ИВЛ | вентиляция, ventilator settings`. Варианты предлагаются на языке
  запроса, но английские термины/аббревиатуры допустимы. Расширенный запрос
  используется и для вектора, и для слов.
- **Перевод для CKM**: если среди источников есть `ckm`, кириллическая часть
  **итогового** запроса (вместе с выбранными расширениями) переводится на английский
  (латиница вроде `FiO2`, `at0004` сохраняется). Это отдельная версия `query_en`
  **только для лексических совпадений** в английских документах; similarity для
  обоих источников считается исходным/расширенным запросом. Перевод показывается
  над выдачей вместе с расширенным запросом. Успешный перевод кэшируется в
  `st.session_state` на время сессии и переиспользуется обеими вкладками; в ключ
  входит системный промпт перевода, поэтому его правка в dev-режиме заставляет
  перевести запрос заново.

Итог: similarity у local и CKM сравнима, а перевод используется только для
буквальных совпадений с английскими текстами CKM. Если LLM нет, CKM ищется
«по смыслу» (об этом ниже).

### Шаг 1. Фильтры

Класс архетипа (`OBSERVATION`, `EVALUATION`…) или тип данных поля (`DV_QUANTITY`…),
плюс выбор источника: local / CKM / оба. Фильтр физически вырезает документы
из массивов — дальше считается только по ним.

### Шаг 2. Смысловая близость (`sim`)

Запрос превращается в вектор, затем считается косинусная близость с каждым документом.
Так как векторы нормированы, это одно умножение матрицы на вектор — быстро даже
для десятков тысяч записей.

`sim` — число от −1 до 1 (на практике 0.2–0.8). Это «насколько про смысл»,
без учёта конкретных слов.

### Шаг 3. Буквальные совпадения (`lex`) — BM25 с морфологией

Смысл иногда «плывёт»: запрос «ИВЛ» модель может не отличить от «вентиляции вообще».
Поэтому добавляется второй сигнал — совпадение слов.

**3.1. Какие слова считаем ключевыми.** Слова длиной ≥4 символа — всегда.
Слова в 2–3 символа — только если они реально встречаются в анкорах базы
(так «ИВЛ» и «ЧСС» проходят, а случайное «на» — нет). Это и есть `token_vocab`.

**3.2. Морфология по префиксу.** Для слов ≥6 букв берутся первые 6 букв и ищется
«начало слова»: `вентиляция` → `вентил*` → находит `вентиляции`, `вентиляционный`.
Для коротких слов — точное совпадение. Шесть, а не пять: с пятью `настройки`
находили `настроение`, а `вес` — `весь`.

**3.3. Один проход по корпусу** (`_scan_lexical_stats`) считает по каждому документу:

- сколько раз каждое ключевое слово встретилось в «стоге» (имя файла + anchor +
  текст без блока misuse);
- сколько из них — только в имени/якоре, а не в теле;
- сколько — в блоке misuse;
- длину документа.

**3.4. Формула BM25** (классика поисковых систем, без внешних библиотек):

```
idf(k)  = log(1 + (N − df(k) + 0.5) / (df(k) + 0.5))   ← редкое слово весит больше
tf-part = tf·(k1+1) / (tf + k1·(1 − b + b·dl/avgdl))    ← частота с насыщением и поправкой на длину
lex_raw = Σ idf(k) · tf-part(k)
```

`k1 = 1.2`, `b = 0.75`. Смысл: десятое упоминание слова добавляет мало;
длинный документ не должен выигрывать только за счёт размера; слово, которое есть
у всех, почти ничего не даёт.

**3.5. Покрытие запроса.** Затем `lex_raw` умножается на `(совпавших слов / всего слов)`.
Если в запросе «настройки ИВЛ», а документ содержит только «настройки» — его лексика
режется вдвое. Раньше одно случайное слово могло поднять документ наравне с полным
совпадением.

**3.6. Нормировка.** `lex` делится на максимум по текущей выдаче → всегда 0…1.
Поэтому вклад лексики ограничен и предсказуем: он не может «перевесить» смысл,
как это было раньше.

### Шаг 4. Штрафы-множители

```
score = (sim + 0.5 · lex) × demotion
```

`demotion` — не вычитание (оно ломало шкалу), а умножение:

- **misuse**: слово запроса встретилось в блоке «НЕДОПУСТИМОЕ ИСПОЛЬЗОВАНИЕ»
  и при этом `sim ≥ 0.3` → `×(1 − 0.5)` = −50 %. Порог по `sim` нужен, чтобы
  случайные совпадения не штрафовали нормальные документы.
- **weak**: все совпадения слова — только в имени файла/якоре, в теле документа
  его нет → `×(1 − 0.25)`.

Оба веса настраиваются в dev-режиме.

### Шаг 5. Отбор: сколько показать и где остановиться

Ранжирование отвечает «кто выше», а отбор — «кого вообще показывать».
Он работает **внутри каждого источника отдельно** (`ui/settings.py`), потому что
шкалы local и CKM несопоставимы напрямую.

1. Сортировка по `score` вниз.
2. Берём верхний документ, затем идём вниз, пока выполняются два условия:
   - разрыв с предыдущим ≤ `gap_max` = `0.10 − 0.05·строгость` (при 0.6 → 0.07);
   - score не ниже `top − band`, где `band` = `0.15 − 0.07·строгость` (при 0.6 → ≈0.108).
   То есть выдача «обрывается» на первой заметной ступеньке — это и есть борьба
   с «внезапно 300 результатов».
3. **Пороги схожести**:
   - документ с буквальным совпадением (`lex > 0`) должен иметь `sim ≥ 0.30`;
   - документ «только по смыслу» — `sim ≥ 0.55`;
   - документ на другом языке (язык документа не совпадает с языком запроса,
     которым считается его схожесть) — `sim ≥ 0.30` (для полей 0.50).
   Почему разные: замеры показали, что короткие тексты полей дают мусорному запросу
   `sim ≈ 0.47–0.51`, а нормальным — 0.5–0.77. Один общий порог либо пропускал мусор,
   либо срезал хорошие результаты. Отдельный кросс-языковой порог понадобился потому,
   что мультиязычная модель даёт русско-английским парам схожесть систематически
   ниже (0.44–0.56 у релевантных CKM-архетипов): без перевода запроса порог 0.55
   оставлял 5 из 20 контрольных запросов, 0.43 — 16, 0.40 — 18, а 0.30 — все 20
   (например, «боль» даёт 0.39). Плата за низкий порог — на мусорных запросах
   тоже что-то находится (у 5 из 7 верхняя схожесть 0.31–0.39), поэтому слабые
   чисто смысловые совпадения (`sim < ADL_SIM_LOW_CONFIDENCE`, по умолчанию 0.45)
   показываются с пометкой «может быть нерелевантным». У полей тексты короткие и
   кросс-языковая близость завышена, поэтому там порог 0.50 (иначе один мусорный
   запрос давал 3 случайных поля).
   Порог считается **по документу** (`pure_floor_by_doc_lang`), а не по источнику:
   в CKM теперь только английские документы, поэтому все они идут по кросс-языковому
   порогу.
4. Если после порогов осталось меньше `min_k` (3 архетипа / 5 полей) — добираем
   следующими по score, но **только прошедшими порог**.
5. Внутри источника — микроперестановка (`reorder_picked_with_simi_preference`):
   специализированный `-simi` архетип поднимается выше «родителя», более новая
   версия `.v2` — выше `.v1`. Делается добавкой `eps = 0.0001`, то есть на порядок
   не влияет, только на порядок при равенстве.
6. **Слияние источников**: сравниваются абсолютные score документов. z-score внутри
   источника (`(score − среднее)/разброс`) считается только для диагностики и
   используется как tie-breaker при точном равенстве score. Слияние по score,
   затем обрезка до `max_results = 10`.
7. **Запас для «Показать ещё»**: кроме основной выдачи отбор возвращает список
   кандидатов (`info["candidates"]`) — те же выбранные документы плюс следующие по
   score в пределах каждого источника, но обязательно **прошедшие порог схожести**
   (шаг 3). Кандидаты упорядочены по score, общий потолок — `extend_k` (в UI 50).
   Поэтому «Показать ещё» никогда не показывает заведомо нерелевантное: если запас
   пуст, кнопка не появляется.

### Шаг 6. Что видит пользователь

- Счётчик результатов, галочки, цветная метка источника (`local` или `CKM`) над
  копируемым id. В сам id префикс источника не входит — копируется только id.
- Под выдачей — кнопка «Показать ещё N»: открывает следующие 5 кандидатов из запаса
  (повторяемо, не больше 50 всего). Счётчик при этом показывает «N из M», где M —
  доступный запас.
- В пользовательском режиме строка «почему показано» не выводится (схожесть и
  совпадения — техническая информация). Вместо неё в контексте результата
  подсвечиваются совпавшие слова, а слабые совпадения помечаются как возможно
  нерелевантные.
- В dev-режиме — легенда с формулой `score = (схожесть + вес × лексика) × штраф`
  и компактная сводка по каждому результату: `score 0.643 = (схожесть 0.62 +
  0.50 × лексика 0.05) × штраф 0.75 (misuse)`, строка «Совпало: файл/якорь/текст»
  и предупреждение о слабом совпадении. Плюс caption с фактическими `gap/band/порог`
  и числом взятых из каждого источника.
- Если пусто — сообщение с действующими порогами и три «ближайших по смыслу»
  подсказки (они не проходят порог, но помогают понять, «мимо» это или
  «чуть-чуть не хватило»).
- Если CKM искался без перевода — предупреждение, что для него отключены
  буквальные совпадения.

### Шаг 7. Языковая логика (почему CKM ведёт себя иначе)

`compute_scores_multilingual` делит документы на «local» и «остальные»:

- local: лексика всегда включена, запрос — русский/расширенный;
- CKM: лексика включается, **только если** английская версия запроса действительно
  без кириллицы. Если перевода нет — остаётся чистая семантика, и она попадает
  под кросс-языковой порог 0.30 (вместо 0.55), а слабые совпадения помечаются
  как возможно нерелевантные. До введения порога «деградированный режим» CKM без
  LLM давал 0–3 результата; теперь находятся и слабые совпадения (например,
  «боль» → `abbey_pain_scale` при схожести 0.39).

### Пример целиком: «настройки ИВЛ»

1. Ключевые слова: `настройки`, `ивл` (последнее — потому что есть в словаре базы).
2. «Настройки ИВЛ» находит документ, где есть только «настройки» → покрытие 0.5 →
   лексика вдвое меньше.
3. Документ «Описание настроения» получает лексику по «настрой…», но: покрытие 0.5,
   редкое слово даёт малый IDF, и он не попадает в «полосу» по score. Плюс, если он
   «чисто смысловой», его срежет порог 0.55.
4. Мусорный запрос («квантовый синхрофазный двигатель») не имеет ни слов в базе,
   ни высокой схожести → 0 результатов.

### Почему от старой схемы отказались

| Было | Проблема | Стало |
|---|---|---|
| `score = sim + бонус − штраф` | штраф зависел от числа слов, вся шкала ехала, выдача прыгала 3 → 138 | штрафы-множители, лексика нормирована 0…1 |
| бонус за каждое совпадение | одно случайное слово = полное совпадение | BM25 + покрытие запроса |
| префикс 5 букв | «настройки» ≈ «настроение» | 6 букв |
| один порог схожести | мусор на коротких текстах проходил | два порога: 0.30 / 0.55 |
| фиксированный top-k | либо 3, либо сотни | отбор по «ступеньке» gap/band + лимит 10 |

## 5. Ответ ИИ (RAG) — коротко

Поиск и генерация разделены, и это осознанно: LLM не ищет, она объясняет найденное.

1. Пользователь отмечает галочками архетипы/поля. В контекст попадают не все
   отмеченные, а первые по релевантности — пока не исчерпан бюджет токенов.
   Бюджет задаётся в dev-панели (`context_tokens_archetypes` /
   `context_tokens_fields`, по умолчанию 10 000 токенов на вкладку).
   Жёсткие предохранители: до 20 архетипов (`MAX_CONTEXT_ARCHETYPES`
   в `ui/tab_archetypes.py`) или 100 полей (`MAX_CONTEXT_FIELDS`
   в `ui/tab_fields.py`).
2. `context_builder` собирает компактный контекст: метаданные (цель/использование/misuse)
   + **релевантные фрагменты структуры**, а не весь документ. Фрагменты выбираются
   лексически и/или векторно под тот же запрос, с бюджетом символов из
   `context_tokens_*` (~3 символа на токен для русского).
3. Первый запрос к LLM: `system_prompt` + `answer_user_prompt` (контекст и вопрос).
   Ответ сохраняется в `dialog_messages`. Уточнение отправляется в той же форме:
   актуальный системный промпт + сохранённая история + новый вопрос. Первая пара
   «контекст+вопрос → ответ» сохраняется всегда, чтобы модель видела, что уже
   было предложено; последующие реплики ограничиваются по длине. Автопродолжение
   оборванного ответа — `continuation_prompt`. Для расширения и перевода системные
   промпты содержат все правила и формат, а пользовательские шаблоны — только
   запрос. В промптах можно использовать `{query}`, `{context}` и `{question}`;
   `{target_lang}` в расширении запроса поддерживается опционально.
4. Чат живёт в левом сайдбаре и всегда соответствует активному разделу:
   у «Архетипов» и «Полей» свои истории, при переключении разделов чат меняется.
   Ширина сайдбара регулируется штатным ресайзом Streamlit. Первый вопрос и
   уточнения показываются одинаково: реплики пользователя — справа, ответы ИИ —
   слева; служебный «КОНТЕКСТ» в чат не выводится. Для отображения хранится
   `{prefix}_chat_messages`, для API — `{prefix}_dialog_messages`.
5. Уточнения идут через тот же композер, что и первый вопрос. Тема уточнения
   определяется моделью по системному промпту; отдельной лексической проверки
   и жёсткого отсева нет. Если вопрос вне темы, модель мягко возвращает к запросу
   и не перечисляет архетипы/поля.
6. Если выбор галочек изменился, чат помечается как устаревший, а композер
   предлагает начать новый разговор с новым контекстом.
7. Длинные ответы: если провайдер сообщает `finish_reason=length`, приложение
   автоматически просит продолжить и склеивает части (до двух раз). Для `corp_async`
   по умолчанию отправляется `max_tokens=4096`, у Ollama жёсткого лимита
   `num_predict` больше нет.

## 7. Где «узкие места» — материал для размышлений об улучшениях

Это не список задач, а карта, где механизм упирается:

1. **Лексический проход — самая дорогая часть.** Один Python-цикл с регулярками
   по всем отфильтрованным документам (~22k полей при поиске по обоим источникам).
   Векторная часть при этом почти бесплатна. Напрашивается предвычисленный
   перевёрнутый индекс «слово → документы» или кэш по запросу.
2. **Пороги откалиброваны эмпирически** на текущих индексах и модели. Смена модели
   эмбеддингов сдвинет шкалу `sim` — пороги придётся перепроверять (для этого есть
   скрипты `sim_dist.py`, `floor_sweep.py`, `bench_new_ranking.py`; их стоит занести
   в репозиторий как «золотой набор»).
3. **Сравнение абсолютных score между источниками** всё ещё эвристическое:
   similarity теперь считается одним запросом, а лексика нормируется глобально,
   но шкалы local/CKM могут различаться из-за языка и состава индекса.
   z-score оставлен только как tie-breaker; для строгой калибровки понадобится
   размеченный набор запросов и калиброванная вероятность релевантности.
4. **CKM без LLM** — заведомо деградированный режим. Локальный кэш переводов
   (словарь часто встречающихся медтерминов) снял бы эту зависимость.
5. **Дедупликация**: версии и SIMI-семейства сейчас только переупорядочиваются,
   но не схлопываются. Для «3–10 результатов» иногда полезнее показать 10 разных
   архетипов, чем 4 версии одного.
6. **Нет оценки качества в CI**: тесты проверяют корректность кода, но не
   «стало ли лучше искать». Метрики вроде recall@10 на контрольных запросах
   и «мусор → 0» дали бы защиту от регрессий.
