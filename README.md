# ADL Smart Search

Локальная RAG-система для семантического поиска по openEHR ADL-архетипам (≈1000 файлов) с ответами LLM.

Текущая версия — **0.9.0**.

## Возможности

- Семантический поиск по базе `.adl` (эмбеддинги `sentence-transformers` + небольшой бонус за ключевые слова).
- Компактный контекст по архетипу (структура + термины из `ontology`).
- LLM-ответ:
  - **МЭШ.ИИ.Хаб** — корпоративный async API (нужен VPN), выбран по умолчанию;
  - **GigaChat** (Сбер) — бесплатный freemium для физлиц;
  - **OpenAI-совместимый API** и **Ollama** — доступны в dev-режиме.
- Инкрементальная индексация: пересчитываются только изменившиеся `.adl`.

## Установка

Создайте виртуальное окружение и установите зависимости:

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

Для установки всех зависимостей в точных версиях (повторяемое окружение) используйте lock-файл:

```bash
pip install -r requirements.lock.txt
```

Lock-файл генерируется из `requirements.txt` утилитой `pip-compile` (входит в `requirements-dev.txt`). После добавления или обновления пакетов регенерируйте его:

```powershell
scripts\compile-deps.ps1          # сохранить текущие версии окружения
scripts\compile-deps.ps1 -Upgrade # пересчитать всё до актуальных версий
```

## Запуск (UI / Streamlit)

Обычный (пользовательский) режим:

```bash
streamlit run app.py
```

Режим разработчика (тюнинг поиска, score/объяснения, Ollama, промпты и т.п.):

```bash
streamlit run app.py -- --dev
```

Либо переменная окружения: `ADL_DEV_MODE=1`. В обоих случаях приложение **сразу стартует**
в режиме разработчика.

При запуске из Python dev-режим доступен всегда: его можно включить переключателем
**«dev-режим»** в правом верхнем углу — перезапуск не нужен.

**В стандартной exe-сборке dev-режима нет.** Переключатель и dev-панель показываются
только в админской сборке, рядом с exe которой лежит маркер `dev_mode.enabled`
(собирается через `.\build_exe.ps1 -WithDevMode`). Пользователь exe не может менять
поисковые настройки, LLM и промпты.

В обычном режиме виджетов настроек нет: приложение работает по базовому `config/`
из репозитория, пользовательским overrides и переменным окружения, а левый сайдбар
отдан чату с ИИ. В режиме разработчика над разделами появляется блок
**«Настройки (dev)»**: папка с `.adl`, папка индекса, индексация, параметры поиска,
LLM и все системные промпты. Все внутренние блоки свёрнуты; в «Поиске» есть кнопка
**«Сбросить настройки поиска»** — она возвращает пороги, веса и лимит результатов
к значениям по умолчанию.

`<data_root>` — папка с `config/` и `data/` внутри Git-репозитория, обычно
`C:\emiastemplates\Soft\ADL Smart Search`.

Промпты хранятся отдельно от поисковых настроек — в `<data_root>/config/prompts.json`.
Файл нужен только для запросов к LLM: поиск, просмотр и индексация работают без него.
Если файл отсутствует или обязательный ключ пуст, ошибка показывается в момент
обращения к ИИ. Текстов промптов в коде нет.

В dev-режиме при запуске из проекта изменения из блока «Настройки (dev)»
сохраняются в базовый `<project>/config/settings.json`, `<project>/config/llm.json`
и `<project>/config/prompts.json` — это админский режим правки конфига.
Совпадающие ключи при этом автоматически убираются из пользовательских overrides,
чтобы `config/` оставался источником истины.

В админской exe-сборке (с маркером `dev_mode.enabled`) промпты и настройки
сохраняются в подключённый внешний `config/`. В стандартной exe dev-панели нет,
поэтому на стороне пользователя сохраняется только путь к репозиторию:

- `%LOCALAPPDATA%\ADL-Smart-Search\config\bootstrap.json` — путь к подключённому репозиторию;
- `%LOCALAPPDATA%\ADL-Smart-Search\config\*.overrides.json` — служебные overrides.

Провайдер ИИ выбирается радиокнопкой в чате: «ГигаЧат» ↔ «МЭШ.ИИ.Хаб».
Выбор действует только в текущей сессии и не сохраняется. При каждом запуске
по умолчанию активен **МЭШ.ИИ.Хаб**. В `config/llm.json` хранятся настройки обоих
провайдеров, но не выбор активного.

При запуске из проекта локальные overrides, bootstrap и логи лежат
в `<project>/.adl-local/config`.

Базовые настройки лежат в `<data_root>/config/settings.json`, `llm.json` и
`prompts.json`, ключи LLM — в `<data_root>/config/.env`. Они обновляются через
`git pull`. Кнопка **«Вернуться к настройкам по умолчанию»** удаляет пользовательские
overrides (с резервной копией) и возвращает значения из базового `config/`;
промпты она не трогает.

При следующем запуске (в любом режиме) настройки собираются как
`config/ → пользовательские overrides`. Секреты (`LLM_API_KEY`,
`GIGACHAT_CREDENTIALS`, `OPENAI_API_KEY`) всегда берутся из окружения/`.env`.
Сам переключатель dev-режима не сохраняется: по умолчанию приложение снова стартует
в пользовательском режиме, если не передан `--dev` / `ADL_DEV_MODE=1`.

## Сборка в .exe (Windows, PyInstaller)

Краткая инструкция по сборке и передаче артефактов: [BUILD.md](BUILD.md).

Цель: дать пользователю максимально простой запуск **без Python и командной строки**.

### Как это работает

- В `dist/ADL-Smart-Search-YYYYMMDD-HHMMSS/` будут лежать `ADL-Smart-Search.exe`
  (launcher), `ADL-Smart-Search-Updater.exe` (обновления) и `version.json`.
- Стандартная сборка **без dev-режима**: пользователь может только временно
  переключить провайдера ИИ в чате (выбор не сохраняется). Dev-панель включается
  админской сборкой `.\build_exe.ps1 -WithDevMode` — рядом с exe появляется
  маркер `dev_mode.enabled`.
- `ADL-Smart-Search-Index.exe` в пользовательскую сборку не входит. Для админской
  сборки используйте `.\build_exe.ps1 -WithIndexer` (можно вместе с `-WithDevMode`).
- При запуске exe:
  - поднимается локальный Streamlit на `127.0.0.1:<порт>`
  - автоматически открывается браузер
  - индексы и базовые конфиги берутся из внешнего приватного Git-репозитория
  - `models/` (кэш embedding-модели) используется рядом с exe
  - при закрытии вкладки процесс завершается через 15 минут; кнопка «Завершить работу» — сразу
- Для офлайн-работы:
  - embedding-модель должна быть уже в `models/`
  - в launcher включён `HF_HUB_OFFLINE=1` и `TRANSFORMERS_OFFLINE=1`

### Подготовка (на машине сборки)

0) **Рекомендация по Python для сборки**: используйте **Python 3.11 или 3.12 (x64)**.
Под Windows это критично для предсказуемой установки `torch`/`sentence-transformers` и работы PyInstaller.

1) Создать venv и поставить зависимости:

```powershell
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
```

Для **повторяемой сборки** рекомендуется использовать зафиксированные зависимости:

- `requirements.lock.txt` — полный список pinned версий (если файл есть, `build_exe.ps1` использует его автоматически). Генерируется из `requirements.txt` через `scripts\compile-deps.ps1` (pip-compile).

Если у вас уже есть `.venv`, но она создана на другом Python (например 3.13), удалите папку `.venv` и создайте заново на Python 3.11/3.12.

2) Один раз убедиться, что embedding‑модель **уже скачана** на машине сборки.

Важно: `.exe` ожидает модель **рядом с exe** в папке `models/` и по умолчанию работает с HF/Transformers в режиме offline.
Чтобы пользователю не пришлось скачивать модель, `build_exe.ps1` при сборке **копирует полный кэш модели** (включая веса в `blobs/`)
из **пользовательского HuggingFace cache** машины сборки в `dist\\...\\models\\...`.

Практически это означает: перед сборкой достаточно один раз запустить dev-версию с интернетом (например `streamlit run app.py`), чтобы модель скачалась в пользовательский кэш.

3) Собрать exe:

```powershell
.\build_exe.ps1 -Mode onedir
```

Результат будет в `.\dist\ADL-Smart-Search-YYYYMMDD-HHMMSS\` (каждая сборка в отдельной папке).

### Индексация без интерфейса (отдельный exe)

`ADL-Smart-Search-Index.exe` **не входит** в пользовательскую сборку. Он нужен
только администратору для индексации. Соберите его отдельно:

```powershell
.\build_exe.ps1 -Mode onedir -WithIndexer
```

Он запускает индексацию в консоли и не поднимает Streamlit. Это тонкий лаунчер:
он запускает основной exe с `--index` и использует его библиотеки из `_internal`,
поэтому не дублирует `torch` и `sentence-transformers`.

Вместо него можно запустить основной exe напрямую:

```powershell
.\ADL-Smart-Search.exe --index --source all --kind all
```

- Если запустить его двойным щелчком (без аргументов), открывается меню с теми же
  вариантами, что в dev-панели:
  1. Локальная база — архетипы
  2. Локальная база — поля
  3. CKM — архетипы
  4. CKM — поля
  5. Индексировать всё (инкрементально)
  6. Полная пересборка (удалить и собрать заново)
  7. Проверить индексы
  8. Показать настройки и статус

- Пути берутся из `<data_root>/config/settings.json` и `<data_root>/config/.env` —
  тех же, что в dev-панели. Пользовательские overrides лежат в
  `%LOCALAPPDATA%\ADL-Smart-Search\config`.
- Модель эмбеддингов ищется в `models/` рядом с exe (офлайн, как у основного приложения).

Для автоматизации в админской сборке можно запускать без меню:

```powershell
# Всё, что настроено в config/settings.json и пользовательских overrides
.\ADL-Smart-Search-Index.exe --source all --kind all

# Только локальная база, только архетипы, инкрементально
.\ADL-Smart-Search-Index.exe --source local --kind archetype

# Полная пересборка всех индексов
.\ADL-Smart-Search-Index.exe --full --source all --kind all

# Проверка и статус без запуска модели
.\ADL-Smart-Search-Index.exe --verify
.\ADL-Smart-Search-Index.exe --list
```

Те же команды доступны из Python: `python -m adl_smart_search.rebuild_index ...`.

### Еженедельное обновление индексов

Индексы и базовые конфиги живут в отдельном приватном Git-репозитории. Пользователи
подтягивают его сами (`git pull`), приложение только читает.

1) Собрать/обновить индексы сразу в репозиторий с данными:

```powershell
.\scripts\build-index.ps1 -AdlDir C:\Archetypes -CkmAdlDir C:\CKM-mirror\local\archetypes -IndexDir C:\path\to\data-repo\data
```

`build_index.ps1` обновит `local\`, `ckm\` и `build_info.json` с датами сборки.
Затем закоммитьте и запушьте изменения в приватный репозиторий.

2) Пользователь делает `git pull` в своём клоне репозитория и перезапускает приложение.
Путь к репозиторию хранится в `bootstrap.json` и не перезаписывается обновлениями.

3) Обновление самого приложения приходит отдельно — через публичные GitHub Releases.
Полный zip для новых пользователей лежит в облаке и **не содержит** `data/` и `config/`.

### Обновление приложения

В exe-режиме приложение раз в сутки проверяет манифест обновлений
(`update/stable.json` публичного репозитория). Если доступна новая версия,
в UI появляется кнопка **«Обновить сейчас»**.

- updater скачивает только изменённые файлы (delta) либо полный архив;
- проверяет SHA-256 каждого файла;
- ждёт закрытия приложения, применяет обновление и перезапускает его;
- пользовательские `data/`, `config/`, `.env` и логи не трогаются.

Локальный процесс завершается по кнопке **«Завершить работу»** или через 15 минут после
закрытия браузерной вкладки (`ADL_IDLE_EXIT_MINUTES`). Повторный запуск exe
открывает уже работающий экземпляр, а не поднимает второй сервер.

Настройки:

- `ADL_UPDATE_FEED=https://.../update/stable.json` — свой манифест;
- `ADL_UPDATE_CHECK=0` — выключить проверку.

Подробности сборки релиза и публикации assets — в `update/README.md`.

### Распространение пользователям

Пользователю отдаётся zip с приложением (см. `-Zip`):

- `dist\ADL-Smart-Search-YYYYMMDD-HHMMSS\` — exe, indexer, updater, `version.json`, `_internal`, `models`, `sertificates`;
- `data\` и `config\` в дистрибутив не входят.

После распаковки пользователь:

1) клонирует/подтягивает приватный репозиторий с данными;
2) запускает `ADL-Smart-Search.exe`;
3) при первом запуске приложение находит репозиторий автоматически или просит указать
   его корень (папку, внутри которой лежат `config/` и `data/`);
4) путь сохраняется в `%LOCALAPPDATA%\ADL-Smart-Search\config\bootstrap.json`.

Исходные папки `.adl` пользователю не нужны — он работает с готовым индексом.
Пересборка индексов в интерфейсе доступна только в dev-режиме и не пишет в общий
репозиторий: для управляемой установки индексы обновляете вы.

#### Где лежат данные, конфиги и модели

```text
<repo-root>\                    ← Git-репозиторий (например, C:\emiastemplates)
  Soft\
    ADL Smart Search\           ← data_root
      config\                   ← settings.json, llm.json, corp_catalog.json, .env
      data\                     ← local\, ckm\, build_info.json

%LOCALAPPDATA%\ADL-Smart-Search\
  config\        ← bootstrap.json, *.overrides.json
  logs\

<папка установки>\
  ADL-Smart-Search.exe
  _internal\
  models\        ← embedding-модель
```

При обновлении приложения папка установки заменяется, а `%LOCALAPPDATA%` и
репозиторий с данными не трогаются.

#### Режим проекта и режим exe

Источник данных зависит не от UI-переключателя «dev-режим», а от того, как
запущено приложение:

| Запуск | `data/` и базовый `config/` | Overrides, bootstrap, логи |
|---|---|---|
| Из папки проекта (`streamlit run app.py`, `python launcher.py`) | `<project>/data`, `<project>/config` | `<project>/.adl-local/` |
| Собранный `.exe` | внешний репозиторий | `%LOCALAPPDATA%\ADL-Smart-Search\` |

`dev-режим` в UI только показывает панель настроек и не меняет источник данных.
Явные `ADL_REPO_ROOT`, `ADL_DATA_ROOT`, `ADL_INDEX_DIR`, `ADL_CONFIG_DIR`,
`ADL_LOCAL_DIR` и `ADL_APP_MODE` имеют приоритет в обоих режимах.

### Как пользоваться (пользовательский сценарий)

1) Распаковать zip `ADL-Smart-Search` в любое место (например `D:\ADL-Smart-Search\`).
2) Один раз подтянуть приватный репозиторий с данными через Git.
3) Запустить `ADL-Smart-Search.exe`.
4) В браузере откроется UI. Если штатная папка не найдена — выбрать корень
   репозитория `emiastemplates` на экране подключения данных.
5) Дальше поиск работает по готовому индексу; обновления индексов — через `git pull`.

В правом верхнем углу есть кнопка **«Завершить работу»** — она останавливает
локальный сервер. Сначала показывается страница «Приложение остановлено», затем
процесс завершается. Вкладку браузера нужно закрыть вручную: сервер не может
закрыть её из соображений безопасности браузера. Если приложение запущено из
PowerShell, окно терминала останется открытым — завершается только процесс
приложения, а не сама оболочка. В собранном exe отдельного окна PowerShell нет.
Если просто закрыть вкладку браузера, процесс завершится автоматически через
`ADL_IDLE_EXIT_MINUTES` (по умолчанию 15 минут). Повторный запуск exe не создаёт
второй сервер: приложение откроет уже работающий экземпляр.

При первом запуске exe проверяет штатное место:

```text
C:\emiastemplates\Soft\ADL Smart Search
```

Внутри должны быть `config/` и `data/`. Если папка найдена, приложение сразу
её использует.

Если её нет, приложение показывает экран подключения и предлагает выбрать
корень репозитория `emiastemplates` через **«Обзор»**. Папка
`Soft\ADL Smart Search` внутри выбранного репозитория уже известна приложению.
Никакого автоматического поиска по диску нет.

Выбранный путь сохраняется в `%LOCALAPPDATA%\ADL-Smart-Search\config\bootstrap.json`:

```json
{
  "repo_root": "C:\\emiastemplates",
  "data_root": "C:\\emiastemplates\\Soft\\ADL Smart Search"
}
```

`repo_root` — корень Git-репозитория, `data_root` — папка с `config/` и `data/`.
Обновления приложения эти пути не перезаписывают.

## Файлы индекса

Индексы хранятся в `data\` папки `data_root`:

```
<repo-root>\
  Soft\
    ADL Smart Search\
      config\
        settings.json
        llm.json
        corp_catalog.json
        .env
      data\
        build_info.json   ← даты сборки по local/ckm и видам индекса
        local\            ← индексы локальной базы
          archetype_data.json
          archetype_vectors.npy
          field_data.json
          field_vectors.npy
    ckm\              ← индексы CKM (те же 4 файла)
```

Корень можно переопределить через `ADL_INDEX_DIR` (для тестов/отладки). В обычной
работе он берётся из найденного `bootstrap.json`.

## Короткие запросы и аббревиатуры (например, "ИВЛ")

Если в базе архетипов аббревиатура **не встречается текстом**, поиск по ней может не найти нужные архетипы (например, в тексте «вентиляция», а в запросе «ИВЛ»).

В UI в разделах поиска есть блок **«Расширение запроса (ИИ)»**:

1. Введите запрос и нажмите **«Предложить расширения»** (тот же ИИ, что для ответов).
2. Просмотрите предложенные термины.
3. Отметьте только те варианты, которые считаете полезными, и нажмите **«Искать»**.

ИИ предлагает до 5 вариантов; по умолчанию ни один не отмечен — выберите
нужные галочками. Если не отмечено ни одного варианта, поиск идёт только по
исходному запросу.

ИИ предлагает варианты на языке запроса. Английские термины и аббревиатуры
(`FiO2`, `CT`, `MRI` и т.п.) тоже допускаются, если они реально используются
в русскоязычной медицине или встречаются в индексе.

При поиске по CKM переводится **итоговый** запрос вместе с выбранными
расширениями. Над результатами показывается расширенный запрос и то, по каким
английским словам реально идёт поиск CKM.

Индекс CKM собирается **только по английским `term_definitions`**. Если у архетипа
есть английская версия и перевод на русский, в индекс попадает английская.
Архетипы без английской версии и переводы на другие языки не индексируются.

В пользовательском режиме под каждым источником видна дата последней индексации
(только дата, `05.10.2026`): на вкладке «Архетипы» — дата индекса архетипов,
на вкладке «Поля» — дата индекса полей, у «Локальной базы» и «CKM» своя.
В смешанном режиме («Локальная база + CKM») даты не показываются: там непонятно,
чья это дата. Дата берётся из времени изменения файла индекса.

## Модель ранжирования и отбора результатов

Выдача строится в два шага: **оценка** документов и **отбор** из них.

### 1. Оценка документа

```
score = (similarity + keyword_bonus × lexical) × demotion
```

- `similarity` — косинусная близость эмбеддингов (MiniLM multilingual).
- `lexical` — BM25-подобная оценка буквальных совпадений, нормированная на лучший
  документ запроса (0..1). Учитывает зоны «имя файла», «якорь», «тело документа»,
  не учитывает блок «НЕДОПУСТИМОЕ ИСПОЛЬЗОВАНИЕ». Вклад документа пропорционален
  доле совпавших слов запроса: совпадение одного случайного слова не поднимает
  документ наравне с полным совпадением. Морфология: для слов от 6 символов
  ищем по префиксу основы («вентиляци*»), короткие слова — только точное совпадение.
- `demotion` — понижение: ×(1 − `misuse_penalty`) за совпадение в блоке
  «НЕДОПУСТИМОЕ ИСПОЛЬЗОВАНИЕ» (при схожести ≥ 0.3) и ×(1 − `weak_match_penalty`),
  если слово нашлось только в имени файла/«якоре», а не в теле документа.

### 2. Отбор результатов

Внутри каждого источника (`local`, `ckm`) документы сортируются по score, и берутся
те, для которых одновременно:

- разрыв с предыдущим не больше `gap_max = 0.10 − 0.05 × строгость`;
- score не ниже `top − band`, где `band = 0.15 − 0.07 × строгость`;
- схожесть не ниже порога: `ADL_SIM_FLOOR` (по умолчанию 0.30) для документов
  с буквальным совпадением и `ADL_SIM_FLOOR_PURE` (по умолчанию 0.55) для
  «чисто смысловых» — чистая семантика требует более высокой схожести,
  иначе в выдачу попадает шум;
- для документов на другом языке (русский запрос → английские CKM-документы
  без перевода) действует более низкий порог `ADL_SIM_FLOOR_PURE_CROSS`
  (по умолчанию 0.30): кросс-языковые пары систематически дают меньшую
  косинусную близость, и общий порог 0.55 отсекал релевантные результаты.
  Для полей порог чуть выше (0.50) — короткие тексты дают завышенную близость.
- если чисто смысловая схожесть ниже `ADL_SIM_LOW_CONFIDENCE` (по умолчанию
  0.45), результат всё равно показывается, но помечается предупреждением
  «может быть нерелевантным».

Если набралось меньше `min_k` — добираем лучшими по score (тоже прошедшими порог).
Источники сравниваются по абсолютному score; z-score внутри источника используется
только как tie-breaker и на порядок не влияет. Первичная выдача ограничена
`ADL_MAX_RESULTS` (по умолчанию 10), а кнопка «Показать ещё» может показать до 50
кандидатов.

### 3. Язык запроса и перевод

- **Схожесть** для `local` и `ckm` считается одним и тем же исходным/расширенным
  запросом. Так `similarity` сравнима между источниками, и ни один источник не
  получает преимущество из-за другого вектора запроса.
- **Перевод** нужен только для буквальных совпадений в `ckm` (английские документы).
  Переводится только кириллическая часть — латинские термины и коды (at-коды, имена архетипов)
  сохраняются как есть. Успешный перевод кэшируется на время сессии (общий кэш
  для обеих вкладок), поэтому повторный поиск по тому же запросу не обращается
  к LLM. Если перевод недоступен (нет LLM) или не удался,
  для CKM используется только семантика, а в UI показывается соответствующая подсказка.
  Такие кросс-языковые документы проверяются по сниженному порогу
  `ADL_SIM_FLOOR_PURE_CROSS` (0.30), поэтому поиск по CKM на русском работает
  и без LLM. Самые слабые совпадения помечаются в выдаче как потенциально нерелевантные.
- Лексическая компонента нормируется глобально по всем источникам: `лексика 1.00`
  означает лучший лексический результат среди всех кандидатов, а не внутри одной группы.

## Настройка LLM: dev-режим или `.env`

### Вариант 1 (рекомендуется): dev-режим + ключи в `.env`

1. Включите переключатель **«dev-режим»** в правом верхнем углу.
2. Раскройте **«Настройки (dev)» → «LLM»**. Там редактируются настройки
   обоих провайдеров — «МЭШ.ИИ.Хаб» и «ГигаЧат»; активный выбирается
   радиокнопкой в чате.
3. Ключи (`LLM_API_KEY`, `GIGACHAT_CREDENTIALS`, при необходимости `OPENAI_API_KEY`)
   положите в `<data_root>/config/.env` (или в локальный `.env` в
   `%LOCALAPPDATA%\ADL-Smart-Search\config`).

Несекретные изменения из dev-панели при запуске из проекта сохраняются
в `<project>/config/llm.json` (админский режим правки конфига), а в админской
exe-сборке — во внешний `config/`. **Секреты в `llm.json` и overrides не сохраняются.**

Выбор провайдера также переключается в сайдбаре чата:
**«ГигаЧат»** ↔ **«МЭШ.ИИ.Хаб»**. Он действует только в текущей сессии и не
сохраняется: при следующем запуске снова активен **МЭШ.ИИ.Хаб**. Настройки
обоих провайдеров при этом остаются в `config/llm.json`.
Рядом с переключателем есть значок «?»: во всплывающей подсказке всегда написано,
что МЭШ.ИИ.Хаб требует активного VPN через КриптоПро NGate, а ГигаЧат работает без VPN.

Чтобы сбросить пользовательские настройки и вернуться к базовому `config/`,
нажмите **«Вернуться к настройкам по умолчанию»** (создаётся backup) или удалите
`%LOCALAPPDATA%\ADL-Smart-Search\config\*.overrides.json`.

### Вариант 2: файл `.env` в репозитории с данными

Подходит, когда настройки задаёт администратор и пользователи не должны их менять.
Ключи лежат в `<data_root>/config/.env` и обновляются через `git pull`:

```
<repo-root>\
  Soft\
    ADL Smart Search\
      config\
        .env          ← секреты LLM
        settings.json
        llm.json
      data\
```

При запуске из Python файл ищется в `%LOCALAPPDATA%\ADL-Smart-Search\config`,
затем в `<data_root>/config`, затем рядом с exe/в текущей папке. Путь можно задать
явно: `ADL_ENV_FILE=C:\path\to\llm.env`.

Пример для корпоративного async API — параметры задаются в dev-режиме
(сохраняются в overrides), в `.env` остаётся только ключ:

```dotenv
LLM_API_KEY=...
```

Настройки OpenAI-совместимого API — скрытый dev-блок «OpenAI-совместимый API
(только dev)»: отдельные base url / model, не пересекающиеся с МЭШ.ИИ.Хаб.
Ключ — `OPENAI_API_KEY` в `.env`. Для Ollama — переключатель «Ollama» в dev-режиме.

### GigaChat (Сбер)

Для физлиц доступен бесплатный Freemium-режим: 365 млн токенов на 12 месяцев
и один поток запросов. Нужен личный кабинет GigaChat API, проект и
авторизационный ключ; scope — `GIGACHAT_API_PERS`.

```dotenv
GIGACHAT_CREDENTIALS=...
```

Остальное (scope, модель, сертификат, проверка SSL, лимиты, контекст) задаётся
в dev-режиме → «LLM» → «ГигаЧат». При запуске из проекта это пишется
в `<project>/config/llm.json`, в собранном exe — в пользовательские overrides:

- модель выбирается из списка: `GigaChat-2` (Lite), `GigaChat-2-Pro`,
  `GigaChat-2-Max`, `GigaChat-3-Lightning`, `GigaChat-3-Pro`, `GigaChat-3-Ultra`;
- Python/httpx не использует хранилище сертификатов Windows, поэтому нужен
  корневой сертификат Минцифры (`Russian_Trusted_Root_CA.cer`). По умолчанию он
  ищется в папке `sertificates` рядом с приложением; путь можно задать в dev-панели.
  Отключение проверки SSL — только для отладки.
- Ключ GigaChat хранится только в `.env`, не в `llm.json`.

В dev-режиме можно включить **«Отдельная модель для перевода и расширения»**:
ответы идут через одну модель, а перевод запроса для CKM и предложение расширений —
через другую (например, ответы на более умной, вспомогательные вызовы на более простой).
По умолчанию используется одна и та же модель. Внутри МЭШ.ИИ.Хаб можно смешивать
модели `aiedu-v2` и `mosgpt`: провайдер вспомогательной модели подставляется из
каталога автоматически. ГигаЧат остаётся отдельным режимом и с МЭШ.ИИ.Хаб не смешивается.

Важно:

- в `.env` лежат **только секреты LLM** (`LLM_API_KEY`, `GIGACHAT_CREDENTIALS`,
  `OPENAI_API_KEY`); все остальные настройки — в `config/llm.json`;
- провайдер по умолчанию — `corp_async` (МЭШ.ИИ.Хаб); для GigaChat переключите
  радиокнопку в чате на время сессии. Выбор не сохраняется между запусками;
  настройки обоих провайдеров хранятся в `llm.json`;
- `ADL_API_BASE_URL_DEFAULT` влияет только на dev-панель (подсказка для corp async);
- `.env` **не переопределяет** переменные, уже заданные в системе, — системные важнее;
- файл читается только при старте: после правок перезапустите приложение;
- не добавляйте `ADL_DEV_MODE=1` в боевой `.env` — включится режим разработчика;
- `.env` не попадает в git, но ключи в нём лучше защитить правами доступа к папке;
- через `.env` задаются параметры приложения (`ADL_*`) и секреты LLM.
  Настройки самого Streamlit (порт, тема и т.п.) сюда не попадают — для них есть
  `.streamlit/config.toml` или обычные переменные `STREAMLIT_*`.

Если обязательные параметры не заданы, при попытке задать вопрос чат покажет
предупреждение со списком недостающих полей.

### Проверка темы уточнений

Тема уточнения определяется моделью по системному промпту. Отдельной лексической
проверки и жёсткого отсева больше нет: вопрос всегда уходит в LLM, даже если в нём
нет точных слов из исходного запроса. Это важно для смежных терминов
(«кровь» → «эритроциты») и переформулировок.

Если вопрос действительно вне темы, ИИ не отвечает по сути: одной фразой мягко
возвращает к запросу и не перечисляет архетипы/поля — списки рекомендаций
в таких ответах не выводятся.

### История уточнений

Диалог всегда имеет одну и ту же форму. Первый запрос — это системный промпт,
сообщение с контекстом и вопросом и ответ модели. При уточнении приложение
отправляет тот же системный промпт, сохранённую историю и новый вопрос.

Первая пара «контекст+вопрос → первый ответ» сохраняется всегда: модель видит,
какие архетипы она уже предложила, и может на них ссылаться. Старые реплики
уточнений могут ограничиваться по длине, но первое сообщение с контекстом
и первый ответ не отбрасываются. Отдельного сообщения с «закреплённым
контекстом» больше нет — контекст уже находится в истории диалога.

### Формат ответа

Системный промпт просит отвечать кратко и структурно: сначала прямой ответ,
затем 1–5 наиболее подходящих архетипов или полей с коротким обоснованием
выбора. Отдельно модель просят точно, посимвольно, приводить имена архетипов
и at-коды — Lite-модели иначе путают названия при большом контексте.

Промпты хранятся в `<data_root>/config/prompts.json` и редактируются в dev-режиме →
**«Промпты»**. Там отдельными блоками лежат: основной системный промпт; промпты,
которыми предзаполняется первое сообщение чата (отдельно для архетипов и полей);
шаблон сообщения с контекстом и вопросом; промпт автопродолжения; системный
и пользовательский промпты расширения запроса; системный и пользовательский
промпты перевода для CKM.
Пользовательские шаблоны расширения и перевода содержат только запрос — правила
и формат заданы в соответствующих системных промптах. В промптах можно использовать
`{query}`, `{context}` и `{question}`; `{target_lang}` в расширении запроса
поддерживается, но в базовом конфиге не используется.
Изменения применяются сразу и сохраняются в `prompts.json`; текстов промптов в коде
нет. Если файл отсутствует или в нём пустой обязательный ключ, поиск продолжает
работать, а ошибка показывается при обращении к ИИ.

### Сколько контекста уходит в ИИ

Чтобы ответы не стоили слишком дорого и не терялись в длинном контексте:

- в ИИ уходят **не все** отмеченные результаты, а первые по релевантности —
  ровно столько, сколько помещается в бюджет токенов:
  по умолчанию **10 000 токенов** отдельно для архетипов и для полей;
- жёсткие предохранители — до **20 архетипов** или **100 полей**, но обычно
  бюджет исчерпывается раньше;
- внутри архетипа берётся до 80 строк и до 8 наиболее близких блоков;
- бюджет считается из расчёта ~3 символа на токен (русский текст). Его можно
  изменить в dev-режиме → «Поиск» → «Контекст для ИИ». Это отдельный бюджет
  именно на ADL-контекст, поэтому остаётся место на системный промпт, историю
  чата и ответ модели.

В dev-режиме в чате видна подпись с текущим бюджетом, а под историей —
статистика токенов последнего ответа (вход/выход/из кэша).

### Длинные ответы и обрезка

- Ollama больше не ограничивает ответ 900 токенами по умолчанию: лимит
  (`num_predict`) применяется только если включить его в dev-режиме.
- Если провайдер сообщает, что ответ оборвался по лимиту токенов
  (`finish_reason=length`), приложение автоматически просит продолжить ответ
  (до двух раз) и склеивает части, убирая повтор на стыке.
- Если обрезка всё же осталась, в конце ответа появляется пометка. В этом случае
  для corp_async выберите модель с подходящим `max_tokens` или поправьте
  `model_kwargs` (JSON) в dev-режиме. Для Ollama аналогично — «Ограничить длину
  (num_predict)».
- Для corp_async параметры генерации можно задавать в `config/corp_catalog.json`
  → `model_kwargs` или в dev-панели. Если параметр уже задан в `model_kwargs`,
  соответствующее поле блокируется и берёт значение из JSON; остальные поля
  остаются доступными для настройки. `temperature` и `enable_thinking` задаются
  внутри `chat_template_kwargs`, остальные параметры — на верхнем уровне.
- Если включена отдельная модель для перевода/расширения, у неё есть свой
  блок «Параметры генерации (перевод/расширение)».
- `enable_thinking` по умолчанию выключен и отправляется только для моделей,
  у которых в `corp_catalog.json` есть `chat_template_kwargs.enable_thinking`.
  Для Qwen3 это не даёт reasoning съесть весь `max_tokens`.
- Если `model_kwargs` не задаёт `max_tokens`, для corp_async отправляется 8192.

## Переменные окружения (сводка)

- `ADL_ENV_FILE`: путь к `.env`, если он лежит не в стандартном месте
- `ADL_APP_MODE`: `dev` (проект) или `exe` (внешний репозиторий); по умолчанию определяется по `sys.frozen`
- `ADL_REPO_ROOT`: корень Git-репозитория (например, `C:\emiastemplates`)
- `ADL_DATA_ROOT`: папка с `config/` и `data/` (например, `<repo-root>\Soft\ADL Smart Search`)
- `ADL_LOCAL_DIR`: каталог пользовательских настроек/логов (для exe по умолчанию `%LOCALAPPDATA%\ADL-Smart-Search`, для проекта — `<project>/.adl-local`)
- `ADL_INDEX_DIR`: корень дерева индексов (внутри `local\` и `ckm\`); обычно задаётся автоматически
- `ADL_CONFIG_DIR`: каталог базовых конфигов (обычно `<data_root>\config`)
- `ADL_USER_CONFIG_DIR`: каталог пользовательских overrides
- `ADL_DIR`: папка с `.adl` (нужна только при индексации)
- `ADL_LANG`: `ru` или `en`
- `ADL_AUTO_STRICTNESS`: строгость авто-выдачи по умолчанию (0.0–1.0, по умолчанию 0.6)
- `ADL_TOP_K`: количество результатов
- `ADL_KEYWORD_BONUS`: вес буквальной компоненты (по умолчанию 0.5)
- `ADL_MISUSE_PENALTY`: понижение за совпадение в блоке misuse (по умолчанию 0.5)
- `ADL_WEAK_MATCH_PENALTY`: понижение за совпадение только в имени/«якоре» (0.25)
- `ADL_MAX_RESULTS`: максимум результатов первичной выдачи (по умолчанию 10; «Показать ещё» — до 50 кандидатов)
- `ADL_SIM_FLOOR`: порог схожести для документов с буквальным совпадением (0.30)
- `ADL_SIM_FLOOR_PURE`: порог схожести для «чисто смысловых» документов (0.55)
- `ADL_SIM_FLOOR_PURE_CROSS`: то же для документов на другом языке (0.30)
- `ADL_SIM_LOW_CONFIDENCE`: ниже этой схожести результат помечается как возможно нерелевантный (0.45)
- `ADL_EMBED_MODEL`: модель эмбеддингов
- `ADL_UPDATE_CHANNEL`: `stable` или `beta`
- `ADL_UPDATE_FEED`: явный URL манифеста обновлений
- `ADL_UPDATE_CHECK`: `0` — не проверять обновления
- `ADL_IDLE_EXIT_MINUTES`: завершить exe после N минут без открытой вкладки (по умолчанию 15; `0` — не завершать)
